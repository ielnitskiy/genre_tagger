# genre_tagger

Отдельный сервис, который берёт жанр исполнителя с Last.fm (`artist.getTopTags`)
и проставляет его в ID3-тег (TCON) всех mp3-файлов этого исполнителя в `/music`.
Не связан с ботом по сети — независимо периодически сканирует файловую систему.
Полное описание архитектуры и алгоритма — в `PLAN.md`. Состояние текущей
кампании по чистке жанров и порядок оставшихся шагов — в `CLEANUP.md`.

## Управление сервисом (шпаргалка)

1. **Настройка (один раз):**
   ```
   cp .env.example .env   # заполнить LASTFM_API_KEY
   docker compose build
   ```
2. **Поставить на cron (один раз)** — контейнер не демон, `restart: "no"`, запускается только так. Пример на 03:00 ночи, с `--force-scan` на всякий случай (см. ограничение 5):
   ```
   crontab -e
   0 3 * * * cd /home/biobojlk/projects/media-server/genre_tagger && /usr/bin/docker compose run --rm genre-tagger --once --force-scan >> /var/log/genre-tagger.log 2>&1
   ```
3. **Разовый ручной запуск** (то же, что делает cron):
   ```
   docker compose run --rm genre-tagger --once
   ```
3a. **Пробный запуск на первых N исполнителях** (проверить, что всё работает нормально, перед тем как отпускать на всю библиотеку) — обрабатывает только первые N папок по алфавиту, остальные не трогает:
   ```
   docker compose run --rm genre-tagger --once --limit 50
   ```
   Повторный запуск с тем же `--limit` не натегирует что-то новое, если эти N артистов уже обработаны (сработает обычный mtime-gate) — это не постраничный обход библиотеки, а именно "первые N" каждый раз.
4. **Пересканировать всё, игнорируя кэш mtime** (не трогая Last.fm и уже проставленные теги):
   ```
   docker compose run --rm genre-tagger --once --force-scan
   ```
5. **Сбросить одного артиста** (форсирует повторный запрос к Last.fm и перезапись его тегов на следующем проходе):
   ```
   docker compose run --rm genre-tagger --reset-artist "Имя Исполнителя"
   ```
5a. **Промаппить одного артиста прямо сейчас** — то же самое, что reset + `--once`, но без скана остальной библиотеки: сразу сбрасывает кэш и обрабатывает только этого исполнителя (запрос к Last.fm + перезапись ID3). Имя должно точно совпадать с именем папки в `MUSIC_DIR`:
   ```
   docker compose run --rm genre-tagger --tag-artist "Имя Исполнителя"
   ```
6. **Посмотреть логи cron-запусков:**
   ```
   tail -f /var/log/genre-tagger.log
   ```
7. **Обновить конфиг** (`MIN_TAG_COUNT`/`MAX_GENRES` в `.env`) — ничего руками пересчитывать не нужно, сервис сам обнаружит смену при следующем запуске и пересчитает жанры из уже сохранённого `raw_response`.
8. **БД** — `./data/genres.db`, создаётся автоматически при первом запуске, ничего вручную инициализировать не надо. Удаление файла = полный сброс кэша всех артистов.
9. **Добавить синоним жанра** (см. "Синонимы жанров" ниже) — правит только файл словаря, реальный пересчёт произойдёт на следующем обычном запуске:
   ```
   docker compose run --rm genre-tagger --add-alias hiphop "hip hop"
   ```
10. **Полностью стереть все жанры** (ОПАСНО, необратимо без бэкапа файлов) — снимает genre-тег со всех mp3 в `MUSIC_DIR` и полностью сбрасывает кэш, все артисты станут "новыми". Без `--yes` ничего не меняет, только показывает, сколько файлов затронет:
    ```
    docker compose run --rm genre-tagger --wipe-all-genres          # dry-run, отчёт в лог
    docker compose run --rm genre-tagger --wipe-all-genres --yes    # реальное удаление
    ```

`SCAN_INTERVAL_SECONDS` в `.env` не используется в этой схеме (это параметр run-loop-режима, которым сервис не пользуется — интервал задаётся расписанием cron).

## Синонимы жанров (ska-punk vs ska punk и т.п.)

`lastfm.py` автоматически схлопывает варианты одного тега, различающиеся
только регистром/дефисом/пробелом/подчёркиванием (`Ska-Punk` = `ska punk` =
`SKA_PUNK`). Но настоящие синонимы без общего написания (`hiphop` без пробела,
`dnb` вместо `drum and bass`) так не поймать — для них нужен ручной словарь
замен, собранный по факту того, что реально встречается в вашей библиотеке:

```
python3 scripts/dump_tags.py --db-path ./data/genres.db
```

Скрипт не обращается к сети и решает две независимые задачи:

**1. Бан-лист (мусорные жанры)** — секция всегда печатается первой:
жанры, реально стоящие в ID3, **по числу треков** (по убыванию — самые
редкие внизу). Это единственная метрика "мусорности в вашей библиотеке":
считает, на скольких ФАЙЛАХ реально стоит каждый уже присвоенный жанр (после
`MIN_TAG_COUNT`/`MAX_GENRES`/алиасов/бан-листа), плюс в скобках — на скольких
артистах. Никакого веса Last.fm здесь нет и не используется. Жанры с 1-10
треками — первые кандидаты на `--ban-genre`/`--ban-below`. `--max-tracks N`
показывает только жанры не более чем на N треках.

**2. Алиасы (дубли написания)** — отдельная от бан-листа задача. Показывает
кандидатов на объединение — теги, похожие по написанию (`difflib`), которые
легко пропустить при простом просмотре списка (`hip hop` / `hiphop`). **В
выводе нет никаких чисел** — ни веса Last.fm, ни числа треков, только сами
имена тегов, сгруппированные по схожести написания. Строится по всем
когда-либо встречавшимся тегам Last.fm, **кроме уже забаненных** — их
`--add-alias` всё равно не примет (в рантайме бан выигрывает), поэтому
предлагать их как кандидатов бессмысленно. `--min-count` отсекает из сравнения
совсем случайный шум по внутреннему (непечатаемому) весу Last.fm. Если передан `--max-tracks N`,
показываются только кластеры, где хотя бы один участник реально нуждается в
разборе (`<= N` треков) — но кластер выводится целиком, включая популярные
варианты (иначе не с кем будет сравнить редкую опечатку).

Две задачи разделяются флагами: `--no-clusters` оставляет только секцию по
трекам (для чистки мусорных жанров, `--ban-below`/`--suggest-bans-file`), а
`--only-clusters` — только кандидатов на объединение (для `--add-alias`), без
списка жанров по трекам. `--cutoff` (0..1, по умолчанию 0.8) регулирует
строгость похожести.

`--ban-below N` — сразу (без review) дописывает в `GENRE_BANLIST_FILE` все
жанры с числом треков `<= N` (мержит с уже существующим бан-листом). Путь к
файлу бан-листа берётся из `--banlist-path`/`$GENRE_BANLIST_FILE`. Удобно для
разового прогона, когда вы уже знаете, что весь хвост — мусор.

Библиотека продолжает расти, поэтому такой аудит придётся делать периодически
— и чтобы не проглядеть в большом списке жанр, который на самом деле хочется
оставить (единственный джазовый исполнитель и т.п.), есть двухфазный процесс
с промежуточным редактируемым файлом вместо немедленного `--ban-below`:

```
# 1. Сгенерировать список кандидатов в текстовый файл (ничего не меняет).
#    Уже забаненные ранее жанры сюда не попадают — видно только новое.
python3 scripts/dump_tags.py --db-path ./data/genres.db --max-tracks 10 \
  --suggest-bans-file ./data/ban_candidates.txt

# 2. Открыть файл и удалить строки с жанрами, которые хотите оставить
nano ./data/ban_candidates.txt

# 3. Применить отредактированный список — уходит в постоянный GENRE_BANLIST_FILE
#    Путь тут /data/... (внутри контейнера), а не ./data/... — см. врезку ниже
docker compose run --rm genre-tagger --ban-genre-file /data/ban_candidates.txt

# 4. Применить: снять забаненное с уже затегированных треков и из БД, без сети
docker compose run --rm genre-tagger --once
```

Настоящие дубли написания (не мусор, а синоним) — это отдельный, следующий
проход, см. "Объединение дублей написания (алиасы)" ниже. Порядок именно такой:
алиасы имеют смысл только для жанров, которые вы оставляете.

**Внимание к путям: `./data/...` и `/data/...` — не одно и то же.**
`dump_tags.py` запускается хостовым python из корня проекта, поэтому файлы ему
передаются как `./data/ban_candidates.txt`. А команды через
`docker compose run` выполняются **внутри контейнера**, где `WORKDIR=/app`, а
директория проекта смонтирована как `./data:/data` — там тот же самый файл
доступен по `/data/ban_candidates.txt`. Если передать в контейнер `./data/...`,
он развернётся в несуществующий `/app/data/...` и команда упадёт с
`No such file`.

Бан-лист (`GENRE_BANLIST_FILE`) — обычный отсортированный JSON, поэтому если
держите `./data` под git (или просто периодически бэкапите), `git diff`
покажет ровно то, что реально добавилось между прогонами — не придётся
вычитывать весь файл целиком, чтобы заметить изменения.

Дальше словарь синонимов правится через сам сервис, без ручного
редактирования JSON — пачкой из файла или по одной паре:

```
docker compose run --rm genre-tagger --add-alias-file /data/alias_draft.txt
docker compose run --rm genre-tagger --add-alias hiphop "hip hop"
docker compose run --rm genre-tagger --remove-alias hiphop
docker compose run --rm genre-tagger --list-aliases
```

Словарь лежит в `GENRE_ALIASES_FILE` (по умолчанию `/data/genre_aliases.json`,
внутри уже смонтированного `./data`, переживает пересоздание контейнера) и
хранится **группами**: главный тег → список вариантов написания, которые к
нему сводятся. Так все варианты одного жанра видны в одной записи, а не
размазаны по всему файлу:

```json
{
  "metalcore": ["matalcore", "mathcore"],
  "hip hop": ["hiphop"]
}
```

`--add-alias VARIANT MAIN` добавляет вариант в группу `MAIN` (создавая группу,
если её ещё нет), `--remove-alias VARIANT` убирает его обратно (группа
удаляется, когда в ней не остаётся вариантов). Обе команды только правят файл
и не сканируют библиотеку. Файлы старого плоского формата
(`{"вариант": "главный тег"}`) по-прежнему читаются и будут автоматически
переписаны в групповой вид при первой же правке через CLI — ручная миграция не
нужна.

Реальный эффект — на следующем обычном запуске (`--once` из cron): изменение
словаря меняет `config_hash`, и сервис, как и при смене
`MIN_TAG_COUNT`/`MAX_GENRES`, локально пересчитывает жанры **всех** уже
обработанных артистов из сохранённого `raw_response` (без единого нового
запроса к Last.fm) и форсирует перезапись ID3 у всех, чей жанр реально
изменился. Т.е. один раз добавленный алиас автоматически лечит уже прометённую
библиотеку целиком, а не только новых артистов.

Побочная польза: подстановка происходит **до** отсечения по `MIN_TAG_COUNT`, и
веса вариантов складываются. Если `matalcore` и `metalcore` набрали по 6 при
`MIN_TAG_COUNT=10`, по отдельности не прошёл бы ни один, а после алиаса
`metalcore` получает 12 и проходит.

Чего `--add-alias` не даст сделать (и почему):
- **Заалиасить забаненный жанр** (или указать забаненный как цель) — в рантайме
  бан выигрывает, так что алиас просто никогда бы не применился. Сначала
  уберите жанр из `GENRE_BANLIST_FILE`. Если конфликт всё же попал в файлы
  через ручную правку, обычный запуск один раз залогирует `WARNING` со списком
  пересечений.
- **Создать цепочку** (`a → b`, где `b` сам является вариантом `c`) — в
  `_filter_tags` подстановка делается одним хопом, поэтому цепочка почти
  никогда не даёт ожидаемого результата. Если цепочка всё же оказалась в файле
  после ручной правки, она разрешается транзитивно при загрузке с `WARNING`, а
  циклы разрываются в no-op.

## Бан-лист жанров

Некоторые теги Last.fm — не синонимы, а откровенный мусор или просто
нежелательные для вас жанры (например, слишком общие или оскорбительные
теги, которые изредка проскакивают у отдельных исполнителей). Для них — не
словарь замен, а список полного исключения:

```
docker compose run --rm genre-tagger --ban-genre "k-pop" trumpet icelandic
docker compose run --rm genre-tagger --list-banned-genres
```

Список лежит в `GENRE_BANLIST_FILE` (по умолчанию `/data/genre_banlist.json`,
внутри уже смонтированного `./data`, переживает пересоздание контейнера).
`--ban-genre` принимает сразу несколько жанров за один вызов (удобно после
разбора вывода `dump_tags.py`) и только правит файл, не сканирует библиотеку. Реальный
эффект — на следующем обычном запуске (`--once` из cron), точно так же, как
при смене `MIN_TAG_COUNT`/`MAX_GENRES`/словаря синонимов: сервис локально
пересчитывает жанры **всех** уже обработанных артистов из сохранённого
`raw_response` (без единого нового запроса к Last.fm), исключая забаненные
теги, и форсирует перезапись ID3. Если у артиста после исключения не остаётся
ни одного жанра, тег genre полностью снимается и с диска, и из БД (не
оставляется как "was, but now null" — файл возвращается в состояние "без
жанра"). Убрать жанр из бан-листа обратно можно только вручную,
отредактировав JSON-файл (как и со словарём синонимов, CLI-команды на
удаление нет).

### `BAN_AFTER_TOP_N` — что делать с освободившимся слотом

По умолчанию (`BAN_AFTER_TOP_N=0`) бан отсекает теги **до** среза по
`MAX_GENRES`, то есть в ID3 уходит «топ-N из незабаненных». У этого есть
неочевидное следствие: бан топового тега освобождает слот, и в него
поднимается следующий тег из хвоста ответа Last.fm — тот, что раньше в ID3 не
попадал вообще. Поэтому **число уникальных жанров в библиотеке после
бан-прохода может вырасти**, а повторные проходы не сходятся: каждый выталкивает
наверх новую порцию хвоста.

`BAN_AFTER_TOP_N=1` меняет порядок: топ-N выбирается по всем тегам, и уже из
него выбрасываются забаненные. Слот не переиспользуется, у артиста просто
становится меньше жанров. Бан-проход становится монотонным — сколько тегов
забанили, столько уникальных жанров и ушло.

Цена — потеря настоящих жанров, стоящих ниже забаненных: у артиста с тегами
`rock` 100, `russian` 90, `punk` 80, `garage rock` 70 при забаненном `russian`
и `MAX_GENRES=3` вместо `rock, punk, garage rock` останется `rock, punk`.
Если забанен весь топ-N, артист остаётся без жанра вовсе, хотя настоящий жанр
в хвосте есть.

Что выбрать — зависит от того, чего в бан-листе больше. Если это в основном
высоковесные не-жанры (гео-теги, служебные метки Last.fm), которые стоят у
артистов в топе, режим `1` даёт предсказуемый результат. Если баните точечный
мусор из хвоста — разница невелика, и дефолт лучше сохраняет жанры. При
высоком `MIN_TAG_COUNT` режимы сходятся: заполнять освободившийся слот
становится нечем.

Встроенный `TAG_BLOCKLIST` (`seen live`, `favorite`, годы) отсекается до среза
в **обоих** режимах — эти теги никогда не занимают слот в топ-N.

Смена `BAN_AFTER_TOP_N` меняет `config_hash`, поэтому следующий `--once`
локально пересчитает жанры всей библиотеки из `raw_response`, без обращений к
Last.fm. Режим можно включить, посмотреть на результат и вернуть обратно.

## Удаление мусорных тегов

```bash
python3 scripts/dump_tags.py --db-path ./data/genres.db --max-tracks 10 --no-clusters \
  --suggest-bans-file ./data/ban_candidates.txt

nano ./data/ban_candidates.txt

docker compose run --rm genre-tagger --ban-genre-file /data/ban_candidates.txt

docker compose run --rm genre-tagger --once
```

Что происходит на каждом шаге:

1. **`dump_tags.py --suggest-bans-file`** — ничего не меняет, только читает уже
   накопленный кэш и пишет в `ban_candidates.txt` список жанров с ≤10 треками
   (с пометкой, сколько треков/артистов у каждого). Уже забаненные ранее
   жанры сюда повторно не попадут.
2. **`nano ban_candidates.txt`** — вручную вычёркиваете строки с жанрами,
   которые на самом деле хотите оставить (например, единственный редкий, но
   настоящий жанр).
3. **`--ban-genre-file`** — читает отредактированный файл и дописывает
   оставшиеся жанры в постоянный `genre_banlist.json`. Библиотеку не
   сканирует.
4. **`--once`** — офлайн (без обращения к Last.fm) пересчитывает жанры всех
   уже обработанных артистов с учётом нового бан-листа: забаненные жанры
   снимаются и с ID3-тегов на диске, и из БД.

**Этот проход делается первым**, до алиасов: алиасы имеют смысл только для
жанров, которые вы оставляете, а сводить два написания жанра, который всё
равно собираетесь удалить, — потерянная работа. Порядок к тому же
поддерживается механикой: `--add-alias` отказывается работать с забаненным
жанром, и забаненные теги не попадают в кандидатов на объединение.

## Объединение дублей написания (алиасы)

Делается **после** бан-прохода, по тем жанрам, которые вы решили оставить.

```bash
python3 scripts/dump_tags.py --db-path ./data/genres.db --only-clusters \
  --suggest-aliases-file ./data/alias_draft.txt

nano ./data/alias_draft.txt

docker compose run --rm genre-tagger --add-alias-file /data/alias_draft.txt

docker compose run --rm genre-tagger --once
```

Что происходит на каждом шаге:

1. **`dump_tags.py --suggest-aliases-file`** — ничего не меняет, только читает
   кэш и пишет заготовку словаря из двух секций: сверху группы, которые
   предположил `difflib` (готовыми строками `главный тег <- варианты`), ниже —
   **все остальные** незабаненные теги, закомментированными, по одному на
   строку в алфавитном порядке.
2. **`nano alias_draft.txt`** — основная работа руками, и обе секции нужны по
   разным причинам:
   - в предположениях `difflib` бывает мусор — он группирует по **написанию**,
     а не по смыслу, поэтому в одну строку могут попасть разные жанры
     (`art rock` / `hard rock`). Лишние строки удаляете, у остальных проверяете,
     что главным тегом стоит нужный (взят первый по алфавиту, не по смыслу);
   - `difflib` в принципе не найдёт синонимы без общего написания
     (`dnb` ↔ `drum and bass`) — их собираете сами из закомментированного
     списка, раскомментировав и оформив строкой `главный тег <- вариант`.
     Алфавитный порядок тут помогает: родственные написания стоят рядом.
3. **`--add-alias-file`** — применяет отредактированный файл в постоянный
   `genre_aliases.json`. Проверки те же, что у `--add-alias`; если хотя бы одна
   строка не проходит, не применяется **ничего** — вы получите список проблем с
   номерами строк и повторите. Библиотеку не сканирует.
4. **`--once`** — офлайн (без обращения к Last.fm) пересчитывает жанры всех
   уже обработанных артистов с учётом новых алиасов: там, где жанр реально
   поменялся, ID3-тег на диске перезаписывается главным тегом.

Для одиночных правок файл не нужен: `--add-alias VARIANT MAIN` добавляет одну
пару, `--remove-alias VARIANT` убирает, `--list-aliases` показывает текущие
группы.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MUSIC_DIR` | `/music` | Корень медиатеки (`{artist}/{album}/{title}.mp3`) |
| `DB_PATH` | `/data/genres.db` | SQLite-кэш "исполнитель уже обработан" |
| `LASTFM_API_KEY` | — (обязательна) | Ключ Last.fm, read-only метод, `LASTFM_SECRET` не нужен |
| `SCAN_INTERVAL_SECONDS` | `86400` | Интервал между проходами в режиме демона (не используется при запуске через cron + `--once`) |
| `MIN_TAG_COUNT` | `10` | Минимальный `count` тега на Last.fm, чтобы не считаться шумом |
| `MAX_GENRES` | `3` | Сколько топ-тегов брать как жанры |
| `GENRE_TTL_DAYS` | `180` | Через сколько дней после `processed_at` заново дёргать Last.fm для уже обработанного артиста (жанры на Last.fm могли поменяться) |
| `SKIP_DIRS` | `download-errors` | Через запятую — top-level папки в `MUSIC_DIR`, которые не считаются исполнителями |
| `GENRE_ALIASES_FILE` | `/data/genre_aliases.json` | Файл со словарём синонимов (группами: главный тег → варианты), см. "Синонимы жанров" выше |
| `GENRE_BANLIST_FILE` | `/data/genre_banlist.json` | Файл со списком запрещённых жанров, см. "Бан-лист жанров" выше |
| `BAN_AFTER_TOP_N` | `0` | `1` — применять бан после среза по `MAX_GENRES` (слот не переиспользуется), см. "Бан-лист жанров" выше. Влияет на `config_hash` |
| `LOG_LEVEL` | `INFO` | Уровень логирования (`DEBUG`/`INFO`/`WARNING`/...); невалидное значение откатывается на `INFO` с предупреждением в stderr |

Смена `MIN_TAG_COUNT`/`MAX_GENRES` между запусками автоматически пересчитывает
жанры уже обработанных исполнителей из сохранённого ответа Last.fm (без новых
сетевых запросов) и форсирует перезапись их ID3-тегов на следующем проходе.

## Известные ограничения

1. **Шум/отсутствие тегов на Last.fm** — часть исполнителей получит `genre=NULL`
   и останется без тега вплоть до `GENRE_TTL_DAYS` (по умолчанию 180 дней), когда
   сервис сам перепроверит жанр у Last.fm. Форсировать раньше — `--reset-artist`.
2. **Расхождение имени папки и канонического имени на Last.fm** —
   `autocorrect=1` помогает частично; жёсткие расхождения (транслитерация,
   "The"-префиксы) дают `genre=None`.
3. **Один жанр на всю папку исполнителя** — сборники/"Various Artists" получат
   один и тот же жанр на все файлы (не обрабатывается в MVP).
4. **`has_genre`-guard на самом первом проходе нового исполнителя** — если у
   файла уже стоял genre до того, как сервис впервые дошёл до исполнителя
   (вручную или из другого источника), Last.fm не перезапишет его. На практике
   почти не встречается, так как spotDL никогда не пишет genre сам.
5. **Надёжность mtime-gate** — алгоритм полагается на то, что изменение
   содержимого папки альбома обновляет её mtime (стандартно для POSIX ФС).
   Если `/mnt/music` смонтирован по сети (NFS/SMB) с нестандартным кэшированием
   атрибутов, это стоит проверить эмпирически после деплоя.
6. **Осиротевшие записи в кэше** — если папку артиста удалить с диска, запись в
   `artist_genre` не удаляется автоматически, только логируется как `WARNING`
   на каждом проходе. Чистить вручную — `--reset-artist`.
