# План: сервис проставления жанров исполнителям (genre_tagger)

## Контекст

В `/music` (общий том между `get_my_music_bot` и `navidrome`) сейчас нет жанров: spotDL при скачивании (`get_my_music_bot/lib/downloader.dart`, `--format mp3 --output {artist}/{album}/{title}`) не проставляет ID3-тег genre вообще — в репозитории бота нет ни одной строчки кода про ID3/genre/mutagen. Библиотека уже накопилась (много исполнителей без жанра), и дальше будет пополняться ботом.

Нужен отдельный сервис, который:
- берёт жанр с Last.fm (ключ уже есть в `media-server/.env` — `LASTFM_API_KEY`, используется Navidrome для обложек/похожих исполнителей, но не для записи тегов в файлы);
- пишет его в ID3-тег (TCON) всех mp3 исполнителя;
- не дёргает Last.fm повторно для уже обработанных исполнителей — хранит это состояние в SQLite;
- сам находит новые альбомы/треки уже обработанных исполнителей и дотегирует их без повторных запросов к Last.fm.

Этот файл — только план. Код, Dockerfile и интеграция в `media-server/docker-compose.yml` реализуются отдельно, позже.

## Решения

1. **Триггер** — независимое периодическое сканирование `/music`, без какой-либо связи с ботом (в проекте нет ни одного межсервисного HTTP/IPC — этот сервис его тоже не заводит, просто читает файловую систему).
2. **Язык** — Python (`mutagen` для ID3, `requests` для Last.fm).
3. **Кэш "уже обработано"** — SQLite-файл (не сервер БД — по ресурсам не отличается от JSON-файла, но удобнее для запросов).
4. **Политика перезаписи и новых треков** — SQLite кэширует только сам факт "жанр для исполнителя X уже выяснен на Last.fm" (это единственная дорогая/лимитируемая операция). Проставление тега в конкретный файл — отдельная, дешёвая проверка по самому файлу: если у mp3 ещё нет genre-тега — значит это новый трек (spotDL никогда не пишет genre сам), и ему просто применяется уже известный жанр из кэша, без обращения к Last.fm. Так исполнитель обрабатывается через Last.fm ровно один раз навсегда, но новые альбомы/треки того же исполнителя всё равно получают тег на следующем скане — без сети, только локальное чтение ID3.

### Алгоритм прохода (`run_once`)

Двухуровневый обход с **mtime-gate на уровне альбома**: папка артиста читается всегда (иначе не узнать про новые альбомы), но *внутрь* альбомной папки заходим (`listdir`) только если её `mtime` изменился с прошлого скана — для неизменившихся альбомов список файлов переиспользуется из кэша без единого обращения к диску.

```
для каждой top-level папки-исполнителя в /music:
    если папка начинается с '.' или в SKIP_DIRS (по умолчанию: download-errors) → пропустить

    album_dirs = список подпапок-альбомов (один readdir верхнего уровня — неизбежен,
                 иначе не узнать о новых альбомах)
    если album_dirs пуст → пропустить (не исполнитель)

    если исполнитель уже есть в SQLite (is_done):
        genres, cached_albums = db.get(artist)   # cached_albums: {альбом: {"mtime": ..., "files": [...]}}
    иначе:
        cached_albums = {}

    current_albums = {}
    new_files = set()
    changed = False

    для каждой album_dir в album_dirs:
        mtime = os.stat(album_dir).st_mtime
        cached = cached_albums.get(имя_альбома)
        если cached и cached["mtime"] == mtime:
            current_albums[имя_альбома] = cached          # альбом не менялся — файлы НЕ перечитываем с диска
            продолжить со следующим альбомом
        # альбом новый или изменился — listdir только этой папки, не всего артиста
        changed = True
        files_in_album = set(относительных путей .mp3 рекурсивно внутри album_dir)
        current_albums[имя_альбома] = {"mtime": mtime, "files": list(files_in_album)}
        если is_done(artist):
            new_files |= files_in_album - set((cached or {}).get("files", []))

    если is_done(artist):
        если не changed:
            продолжить со следующим исполнителем     # ни один readdir внутрь альбомов не делался вообще
    иначе:
        genres = lastfm.resolve_genres(имя_папки)     # список из ≤3 тегов, None если не нашлось/всё отфильтровалось
        new_files = множество всех files из current_albums.values()   # первый проход — новые все файлы
        db.mark_done(artist, genres, current_albums, raw_json, timestamp)   # запрос сделан один раз навсегда

    если genres не None:
        для каждого файла в new_files:                 # ТОЛЬКО новые/незнакомые пути, не вся папка
            если tagger.has_genre(файл) → пропустить (safety-belt, см. ниже)
            иначе: tagger.write_genre(файл, genres)

    если это была ветка "уже есть в SQLite" и changed:
        db.update_albums(artist, current_albums)       # полная замена — удалённые альбомы естественно выпадают
```

Важно:
- Исполнитель помечается "done" даже при `genres = None` (не найден на Last.fm / все теги отфильтрованы) — иначе такие исполнители запрашивались бы у Last.fm на каждом проходе бесконечно.
- `mtime`-gate экономит именно то, что раньше было неизбежным: `readdir` внутрь *каждой* альбомной папки на *каждом* проходе, даже если она не менялась годами. Теперь для стабильного альбома тратится только `stat` его собственной папки (для сравнения mtime), а список файлов берётся из уже сохранённого в SQLite JSON — без единого обращения к содержимому папки.
- Точный diff по путям (`files_in_album - cached_files`) внутри изменившихся альбомов остаётся как раньше: если в альбом с 500 треками добавили 1 новый, ID3 открывается только у этого одного файла, а не у всех 501 — просто теперь этот diff считается на уровне альбома, а не всего артиста.
- `current_albums` строится заново на каждом проходе только из тех `album_dirs`, что реально существуют на диске сейчас — поэтому удалённые альбомы автоматически выпадают из следующей записи в БД при `db.update_albums`, никакого отдельного "сборщика мусора" для устаревших путей не нужно.
- `tagger.has_genre` внутри `new_files`-цикла — не основной механизм обнаружения новизны (это делает diff путей), а safety-belt: страховка на случай, если путь всё же оказался с уже проставленным тегом (например, вручную).
- **Допущение, требующее проверки на реальном деплое**: gate полагается на то, что добавление/удаление файла внутри альбомной папки обновляет `mtime` именно этой папки (стандартное поведение POSIX-файловых систем). Если `/mnt/music` на хосте смонтирован по сети (NFS/SMB) с нестандартным поведением кэширования атрибутов, `mtime` может не отражать изменения вовремя — тогда gate ложно решит "альбом не менялся" и пропустит новые треки до следующего события, которое всё же тронет mtime (или до `--reset-artist`). Стоит проверить эмпирически после деплоя, прежде чем полагаться на gate как единственный механизм.

### Last.fm (`lastfm.py`)

- `GET http://ws.audioscrobbler.com/2.0/?method=artist.getTopTags&artist=<имя>&api_key=<ключ>&format=json&autocorrect=1`
- Только `LASTFM_API_KEY` — метод read-only, секрет/подпись не нужны (нужны только для scrobbling/OAuth, не для getTopTags). Значит `LASTFM_SECRET` из `.env` этому сервису не требуется.
- Фильтрация шума в тегах (Last.fm — теги от пользователей, там вперемешку жанры и мусор типа "seen live", "favorite", года):
  1. Нет тегов / ошибка ("artist not found") → `None`.
  2. Отбросить теги из небольшого blocklist'а (`seen live`, `favorite`, `favourites`, `love`, `spotify`, `male vocalists`, `female vocalists`, и т.п.) плюс всё похожее на год/декаду (`^\d{2,4}s?$`).
  3. Отбросить теги с `count < MIN_TAG_COUNT` (по умолчанию 10).
  4. Взять топ-3 из оставшихся (регулируется `MAX_GENRES`, по умолчанию 3) как значение жанра.
- Троттлинг: простой sleep-based лимит ≤5 запросов/сек (бэкфилл — единственный всплеск, работает в фоне без спешки). Таймаут запроса ~10с, пара ретраев на сетевых ошибках/5xx, дальше — трактовать как `genre=None`, не падать.

### Запись тега (`tagger.py`)

```python
def has_genre(path) -> bool:
    try:
        tags = EasyID3(path)
    except ID3NoHeaderError:
        return False
    return bool(tags.get("genre"))

def write_genre(path, genres: list[str]):
    try:
        tags = EasyID3(path)
    except ID3NoHeaderError:
        tags = EasyID3()
    tags["genre"] = genres          # EasyID3 пишет список значений как несколько TCON-полей
    tags.save(path, v2_version=4)   # явно ID3v2.4 — только в нём Navidrome гарантированно
                                     # разбирает multi-value TCON на отдельные жанры
```

Только `.mp3` (spotDL всегда выдаёт `--format mp3`), поэтому `EasyID3` без ветвления по форматам. `has_genre` — дешёвая локальная проверка (без сети), на которой держится и защита от лишней перезаписи, и автоматическое дотегирование новых треков уже обработанных исполнителей. Ошибка записи одного файла — лог и `continue`, не прерывает всего исполнителя.

### SQLite (`cache.py`)

Файл **не внутри `/music`** (чтобы не засорять медиатеку служебным состоянием) — по аналогии с `media-server/config/navidrome/`: `media-server/config/genre-tagger/genres.db`, в контейнере смонтирован как `/data/genres.db`.

```sql
CREATE TABLE IF NOT EXISTS artist_genre (
    artist        TEXT PRIMARY KEY,   -- точное имя top-level папки
    genre         TEXT,               -- NULL, если не найдено/отфильтровано; иначе JSON-массив до 3 тегов
    albums        TEXT NOT NULL,      -- JSON-объект {имя_альбома: {"mtime": float, "files": [пути...]}}
    raw_response  TEXT,               -- сырой JSON от Last.fm, для отладки
    processed_at  TEXT NOT NULL
);
```

Одно поле `albums` заменяет собой то, что раньше было плоским списком `files`, — новых колонок не добавляется, просто меняется форма JSON внутри уже существующего поля (mtime нужен только как gate перед listdir, отдельная колонка под него не нужна).

- `is_done(artist) -> bool`
- `get(artist) -> (genres: list[str] | None, dict[str, dict])` — оба значения получены из `json.loads(...)`; второе — `{album: {"mtime", "files"}}`.
- `mark_done(artist, genres: list[str] | None, albums: dict, raw_json, timestamp)` (`INSERT OR REPLACE`, `genres`/`albums` сериализуются в JSON) — вызывается один раз, при первом резолве артиста через Last.fm.
- `update_albums(artist, albums: dict)` (`UPDATE ... SET albums=?`) — вызывается после прохода по изменившимся альбомам уже известного артиста; не трогает `genre`/`raw_response`/`processed_at`. Полная замена (не merge) — удалённые с диска альбомы естественно выпадают из следующей записи.
- `reset(artist)` (`DELETE WHERE artist=?`) — ручной эскейп-хэтч через `--reset-artist`.

При масштабе библиотеки в 1-2ТБ (сотни тысяч треков) JSON-объект на артиста — это десятки КБ максимум даже для самой крупной дискографии, что пренебрежимо мало на фоне самой музыкотеки; хранить пути, а не только их число, окупается тем, что позволяет находить именно новые файлы точным diff'ом внутри изменившегося альбома, не открывая ID3 остальных.

### Docker / деплой

`genre_tagger/Dockerfile` — `python:3.12-slim`, `pip install mutagen requests` (с пинами), `PYTHONUNBUFFERED=1` (чтобы логи сразу шли в `docker compose logs`, как у остальных сервисов стека).

Новый сервис в **`media-server/docker-compose.yml`** (рядом с `navidrome`, т.к. делит с ним `/mnt/music` и `LASTFM_API_KEY` из общего `.env`; `get_my_music_bot` уже доказывает, что хост умеет билдить образы из исходников через `build:`):

```yaml
  genre-tagger:
    build: ../genre_tagger
    container_name: genre-tagger
    environment:
      - MUSIC_DIR=/music
      - DB_PATH=/data/genres.db
      - LASTFM_API_KEY=${LASTFM_API_KEY}
      - SCAN_INTERVAL_SECONDS=86400
      - MIN_TAG_COUNT=10
      - MAX_GENRES=3
    volumes:
      - /mnt/music:/music
      - /home/biobojlk/projects/media-server/config/genre-tagger:/data
    restart: unless-stopped
```

Разовый бэкфилл без изменения compose: `docker compose run --rm genre-tagger --once`.
Интервал сканирования — раз в сутки (`86400`) достаточно: новые исполнители появляются только когда бот что-то скачивает, догонять раз в минуту как Navidrome смысла нет. Navidrome сам подхватит изменённые теги на следующем скане (`ND_SCANSCHEDULE=1m`) — координация не нужна.

### Известные ограничения (зафиксировать в README сервиса)

1. **Шум/отсутствие тегов на Last.fm** — часть исполнителей получит `genre=NULL` и останется без тега; они тоже помечены "done" и не ретраятся автоматически (Last.fm мог просто не знать артиста на момент запроса). Эскейп-хэтч: `--reset-artist "<имя>"` удаляет запись из SQLite и форсирует повторный запрос к Last.fm на следующем проходе.
2. **Расхождение имени папки и канонического имени на Last.fm** — `autocorrect=1` частично помогает, жёсткие расхождения (транслитерация, "The"-префиксы) дают `None`.
3. **Один жанр на всю папку исполнителя** — если когда-нибудь появится сборник/"Various Artists", всем файлам внутри уйдёт один и тот же жанр (не обрабатывается в MVP).
4. **`has_genre`-проверка действует и на первом проходе для нового исполнителя** — если у файла уже стоял какой-то genre до того, как сервис впервые добрался до этого исполнителя (вручную проставленный или из другого источника), он не будет перезаписан данными с Last.fm. На практике почти не встречается: spotDL никогда не пишет genre сам, так что на момент первого прохода тега обычно просто нет. Если нужно, чтобы Last.fm был безусловным источником истины даже поверх таких тегов — на первом проходе для нового исполнителя нужно писать без проверки `has_genre` (отдельная ветка в коде).

## Решённые вопросы (были открытыми)

1. **Смена `MIN_TAG_COUNT`/`MAX_GENRES` не переигрывает уже обработанных исполнителей** — решено: при старте сервиса конфиг (`MIN_TAG_COUNT`, `MAX_GENRES`) хешируется и сравнивается со значением, сохранённым в SQLite с прошлого запуска (новая таблица `meta` или строка `key/value`, например `config_hash`). Если хеш изменился — для всех артистов с непустым `raw_response` фильтрация (blocklist + `MIN_TAG_COUNT` + топ-`MAX_GENRES`) пересчитывается **локально из уже сохранённого `raw_response`**, без единого запроса к Last.fm, и результат перезаписывается в `genre`. Ставится тот же force-rewrite флаг, что и в решении вопроса 4 (см. ниже), чтобы новые жанры реально попали в ID3-теги файлов, а не только в БД. Артисты без `raw_response` (уже были `genre=NULL` из-за сетевой ошибки) — не пересчитываются, это не related к фильтрации.

2. **Гонка между ботом-загрузчиком и сканером** — решено: не гадать о внутреннем поведении spotDL (внешний Python CLI, не в этом репо — в `get_my_music_bot/lib/downloader.dart` есть только вызов процесса, не логика записи файла). Вместо этого `tagger.has_genre`/`write_genre` оборачиваются в `try/except` вокруг открытия ID3 (`mutagen.MutagenError` и `OSError`/битый файл): при ошибке — лог `warning` и `continue`, файл остаётся в `new_files` этого альбома неявно (не добавляется в `cached albums["files"]` для этого прохода — попадёт в diff повторно на следующем скане, т.к. `mtime` папки, скорее всего, ещё раз изменится при дозаписи). Дёшево, не требует знания о поведении spotDL, устойчиво к любому способу записи файла.

3. ~~Имя артиста не экранируется для Last.fm-запроса~~ — не открытый вопрос, а прямой фикс: `lastfm.py` использует `requests.get(url, params={"artist": name, "api_key": ..., ...})`, никогда не интерполирует имя вручную в строку URL.

4. **`has_genre` блокирует re-tag уже протегированных файлов даже после `--reset-artist`** — решено: `--reset-artist` (и пересчёт из решения вопроса 1) ставит артисту флаг `force_rewrite` (доп. колонка в `artist_genre` или отдельная таблица `pending_force_rewrite(artist)`), который снимается после первого успешного прохода. Пока флаг установлен, `write_genre` вызывается для всех файлов артиста безусловно, `has_genre`-guard (safety-belt) для них не применяется — именно на этот один проход. В остальное время (обычный первый проход нового артиста, обычное дотегирование новых треков) `has_genre` продолжает работать как раньше.

## Открытые вопросы

5. **Надёжность `mtime`-gate на реальной ФС** — см. пометку в разделе алгоритма: gate предполагает, что изменение содержимого альбомной папки обновляет её `mtime`. Стоит проверить это эмпирически на конкретном `/mnt/music` после деплоя (локальный диск/NAS/сетевой mount — от этого зависит, насколько gate надёжен). Решается только на этапе деплоя, не на этапе планирования.
